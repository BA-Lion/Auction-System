# 07 列表检索与分页

所属基线：[v1.1](./README.md)。列表允许延迟，进入场次后使用运行状态，付款使用数据库订单事实。

## SEARCH-01 ES 的定位

数据库继续作为权威持久化存储。ES 是用户进入拍品列表时的派生查询服务，用于关键词搜索、条件过滤、排序和分页，不承担竞拍裁决、资金或正式结果权威。

ES 独立作为基础服务部署，多个业务实例共享，不把 ES 当作每个业务实例内部附带的一份独立搜索副本。开发环境可同机部署，正式资源及可用性安排待定；增加业务实例不会自动提高 ES 容量。

选择 ES 是为了组合查询与分页能力，不宣称所有查询都比数据库更快。数据库和 ES 的具体版本、索引分片数与副本数尚未冻结。

## SEARCH-02 数据来源和更新

报价链路为 Redis 接收 → pending／inflight → Kafka → 数据库提交 → ES 同步。商品和场次等其他持久化变化同样从数据库提交结果同步到 ES。

- 不能绕过数据库，仅以 Redis 的最高价直接认定 ES 获得了权威持久化数据。
- 具体采用 CDC 还是数据库事务 Outbox 尚未决定；若用 Outbox，不能照搬资金任务 round_id + user_id 的唯一键。
- 同步需要处理重放、更新乱序、删除、失败恢复及全量重建。
- 更新较新的场次数据后，迟到旧事件不能把价格、截止和状态覆盖回去；多类字段的版本如何合并需要详细设计。
- 报价明细落库与数据库当前状态更新的行为见 03，ES 不自行猜测正确最高价。

已讨论的列表字段包括场次／拍品身份、标题、分类、卖家、开始及截止时间、状态、当前价格、出价次数与更新时间。每场一文档是建议，不是已冻结的索引 schema；文档粒度、可筛选字段、分词、排序及版本字段在详细设计确定。

## SEARCH-03 查询分工和延迟

| 用户行为 | 主要来源 | 时效口径 |
| --- | --- | --- |
| 拍品列表搜索与翻页 | ES | 数据库派生并允许延迟 |
| 进入具体场次看实时价格和截止 | Redis 运行状态及 WebSocket | 当前运行状态，仍有传输延迟 |
| 本人竞价期间的近期回执 | 按 user_id 组织的 Redis 缓存 | ACCEPTED／RECORDED 可短暂落后 |
| 查询订单、付款、流水 | 数据库 | 持久化业务事实 |

筛选、排序和分页必须在同一查询视图内完成。不能先分页，再逐条查询 Redis 并按最新价重新过滤，导致缺页、排序错误或无法解释的总数。

列表显示 100 元、进入场次发现最新为 120 元是允许的延迟表现，出价仍由实时 Lua 决定。不要因为列表价未更新就让旧报价绕过最新价校验。

端到端延迟包括报价待发、Kafka 消费、数据库提交、ES 同步及 refresh；不能拿单一 refresh 间隔当成整条链路的延迟保证。目前未给定秒级 SLA。

## SEARCH-04 PIT + search_after

采用 PIT 与 search_after 作为同次浏览稳定翻页的方向。PIT 固定的是 ES 当时已可见的文档视图，不是给每个用户复制整份文档库，也不包括尚未同步到 ES 的报价。

一次查询会话需要固定以下内容：查询条件、排序规则、PIT、上一页末条排序位置；如果条件包含“当前正在竞拍”等时间判断，还需要固定绝对时间 T0，不能每次翻页重新取 now 而改变结果集合。

后续页面继续使用该查询会话，传递上页末条完整排序值，使用最新返回的 PIT ID。排序必须能稳定区分同值记录，具体选择业务唯一字段或 PIT 提供的平局处理信息在实现中明确。

同一次浏览不为追逐最新价格而强行重排；刷新或修改筛选条件开启新查询。若未来在列表卡片上实时更新价格，需要另外决定显示价与快照筛选价不一致的产品语义，本轮未选。

search_after 适合下一页／加载更多；不承诺任意页码直接跳到深页。上一页、跳页、总数准确性等交互仍待产品细化。

## SEARCH-05 多实例查询会话

实例 A 返回第一页，实例 B 应能处理下一页。PIT 上下文由 ES 保存；后端需要通过受校验游标或共享会话保存查询条件、时间、PIT 与排序位置，不把全部会话状态只放在 A 的内存。

用户请求经过后端的身份与参数校验，不直接向浏览器暴露可任意查询 ES 的入口。游标签名、共享存储、并发翻页以及会话关闭方式未冻结。

## SEARCH-06 五分钟不是已验证容量承诺

用户提出希望 PIT 五分钟内可用，当前仍是待验证参数。ES keep_alive 的续期机制与应用设定的“同一浏览快照总寿命”是两件事。

旧稿提出总寿命最多五分钟作为候选方案；本基线不把它改写成已经确认的最终产品限制。需要同时决定活跃翻页是否续期、空闲多久过期、总寿命上限和失败提示。

无论选哪种时长，失效后不能拿一个新 PIT 冒充旧视图接着翻页。应明确提示重新查询。刷新时关闭旧 PIT，离开页面尽力关闭，服务端超时负责回收未显式关闭的上下文。

PIT 增加旧 segment 保留、有效性状态、文件句柄、堆和磁盘压力，翻页本身仍有查询成本。实际容量取决于活跃 PIT 数、查询 QPS、分片数、数据量、更新速率及持有时长，不能仅按业务服务实例数推算。

详细设计需要在实际索引和更新负载下评估不同保留时长，对比 P95／P99、内存与 GC、磁盘、句柄和回收。Rally 可作为压测工具选项；本文没有引用某个公开测试数字作为本系统容量保证。
