# 08 运维、核对与验收依据

所属基线：[v1.1](./README.md)。本文件汇总必须被后续实现覆盖的行为，不代表已经运行验收测试。

## OPS-01 积压数量限流

积压机制采用数量口径，不用最老等待时间替代已选触发条件。

| 位置 | 观察口径 | 动作方向 |
| --- | --- | --- |
| Redis 待发 | 每逻辑队列 pending + inflight 条数 | 达容量阈值时在 Lua 写入前拒绝繁忙请求 |
| Kafka | 按消费组和 partition 的 lag | 达阈值告警，根据受影响范围限流 |
| failed | 各逻辑队列条数及总量 | 超阈值告警，排查并安排原身份补发 |

未收录的请求得到明确繁忙反馈；已收录事件继续处理。限流范围、阈值、恢复水位、防抖与后台信号下发方式待定。入口基础防刷可以由 NGINX 承担，但它不能直接代替这些业务积压判断。

## OPS-02 异常隔离与人工接管

| 异常 | 当前原则 |
| --- | --- |
| 单笔报价无法确认投递 | 保留完整事件，按预算进入 failed，继续其他独立事件 |
| 单条历史明细异常 | 隔离、记录、告警及补写，不自动停掉所有竞拍 |
| Kafka 整体不可用 | 退避告警并控制接收增长，不机械搬空到 failed |
| 资格数据库回查失败 | 明确表示暂不能确认资格，不伪造未报名负缓存 |
| 截止同步失败 | 保留标记，后台接管，不回退已生效的运行截止 |
| ES 落后或 PIT 失效 | 列表允许延迟或重查，不改变出价和付款规则 |
| 当前领先状态／正式结果证据冲突 | 保存证据、核对恢复或人工处理，不当作无关历史缺失 |
| 资金任务重投 | 依赖事务、原流水号和业务键，冻结、解冻、扣款、入账及平台收入不重复 |

用户允许管理员及运维接管异常，默认不因任意历史缺口自动全场停拍。是否暂停特定场次、何时冻结结算、恢复权限和操作流程尚未完整确定。系统不能在自身裁决数据缺失时凭空继续给出“有效报价”或“正式成交”的确认。

当前不实施“发现某物理 Redis 连续失败便自动迁槽并改变业务路由”的自定义容错方案。Redis Cluster 自身故障恢复、业务恢复及告警应分别设计。

## OPS-03 可检测性与证据边界

Kafka 记录、数据库明细、Redis 待发／异常记录及独立审计信息可用于发现某些差异。比较前必须界定相同的输入范围和处理进度，区分正常异步延迟与真实缺失。

- bid_id 是报价身份，可核对存在性、重复及内容冲突。
- 版本用于状态先后和差异线索，不把 Kafka offset 非连续直接当成业务丢失。
- 不只比较最高价；当前最高价正确不证明所有历史明细完整。
- 可以从已有可靠事件重放数据库缺失记录，补发保持原身份。
- 不假设所有已回执报价都存在于 Kafka：AOF everysec、复制滞后及 Kafka 前窗口仍可能损失数据。
- 如果记录及全部独立证据同时丢失，系统无法无条件识别；“有监控”不等于“任何丢失都能查出”。

核对任务的周期、封闭范围、校验摘要、证据保留时间及自动修复边界待详细设计。

## OPS-04 健康与容量

取消旧汇总端后，关注实际存在的模块：NGINX、业务实例、WebSocket、Redis、报价转发器、Kafka 消费组、截止同步、关场调度、资金扫描和 ES 同步。

需要能识别任务长期不工作、实例退出、连接异常、积压和同步滞后；具体心跳、探针与报警阈值未定。不把“进程活着”当作业务正在推进。

容量验证按接入吞吐、同时开拍数、单场 Lua、单容量 inflight 等 ACK 的发送能力、数据库、在线连接／广播扇出和 ES 查询分别进行。用户尚未给出目标数字，因此任何默认机器数、QPS 或并发用户数都不能作为已经确认的指标。

## QA-01 验收方式

后续验收围绕可观察结果：接口反馈、快照、事件、数据库业务状态和资金余额。故障注入应验证重启、超时、重复和乱序下的最终效果，不以仅检查某个内部函数被调用作为通过标准。

以下是根据已确定行为整理的验收依据；测试框架、测试文件、执行计划和具体压测门槛不在本基线选择。

| 编号 | 场景 | 预期外部结果 |
| --- | --- | --- |
| QA-01 | 同场多实例并发报不同金额 | 按 Lua 实际执行顺序裁决，已接受的最高价不被后执行低价覆盖 |
| QA-02 | 已存在有效报价时再报同价或低价 | 拒绝且不新增有效报价事件 |
| QA-03 | 资格缓存 nil／0／1 | 分别回查／拒绝／继续；nil 分支第一次不写报价 |
| QA-04 | 报名成功与负缓存回填并发 | 迟到空值不覆盖已写资格；不得重复冻结押金 |
| QA-05 | 数据库回查超时 | 不写资格 0，不当成未报名 |
| QA-06 | 网关截止前收到，Lua 截止后执行 | 按执行时点拒绝 |
| QA-07 | 待发已满 | 报繁忙，不先改变最高价再失败 |
| QA-08 | Lua 响应丢失或运行异常 | 不盲目声称一定未执行，不自动换 ID 重提 |
| QA-09 | 尾盘有效涨价 | 截止加 30 秒，次数和版本增加一次，事件包含结果 |
| QA-10 | 第五次加时及随后出价 | 明确最后一次通知，第六次不继续延长 |
| QA-11 | 截止同步时再次加时 | 新标记不被旧任务清除，数据库最终可追到新截止 |
| QA-12 | 最后一笔加时后同步实例退出 | 无后续报价也能通过后台发现未完成任务 |
| QA-13 | 关场与加时报价竞争 | 谁先原子执行决定结果；旧数据库截止不能关掉已加时场次 |
| QA-14 | 领取 pending 后转发器退出 | 接管先恢复 inflight，不丢在弹出与写入之间 |
| QA-15 | Kafka ACK 丢失 | 允许重投，数据库明细及个人确认不重复产生业务效果 |
| QA-16 | 三次应用重试耗尽 | 完整报价进入 failed，后续可继续，补发不变 bid_id |
| QA-17 | 个人确认早于 RECEIVED 写入 | 状态保持 CONFIRMED，不被迟到写降级 |
| QA-18 | 多个 WebSocket 实例与重连 | 同场消息能分发；用户通过快照恢复并过滤旧版本 |
| QA-19 | 数据库收到较旧报价晚于新报价 | 保存所需明细但当前价、截止等不回退 |
| QA-20 | 翻页期间价格和状态更新 | 同 PIT 视图稳定；刷新开启新视图，详情读实时状态 |
| QA-21 | 下一页进入另一业务实例 | 查询条件、排序、PIT 与游标仍可正确续接 |
| QA-22 | PIT 过期或不可用 | 明确重查，不悄悄混入新的结果集合 |
| QA-23 | 重复充值／报名 | 同业务键只充值／冻结一次 |
| QA-24 | 正常付款与超时任务并发 | 只产生一个互斥的订单结果及相应资金效果 |
| QA-25 | 尾款余额不足 | 全事务回滚，未错误结算给卖家 |
| QA-26 | 零尾款建单与超时兜底重复 | 正常成交一次，直接消耗冻结押金，记录完整成交价的付款及平台收入 |
| QA-27 | 解冻、补偿任务重投或人工重放 | 原身份与业务约束生效，不重复释放、扣冻结、卖家入账或计平台收入 |
| QA-28 | ZSet 漏写或丢失 | 每日数据库扫描可补出到期任务，过期付款仍被拒绝 |
| QA-29 | Broker ACK 后资金业务迟迟未完成 | Outbox 不因 ACK 假成功，按 10 分钟规则补发 |
| QA-30 | 第五次资金补发及迟到成功 | 给第五次观察窗口；死信状态不能覆盖 SUCCESS |
| QA-31 | 旧场超时任务迟到，新场已开始 | 不把新场关联拍品状态错误改回待拍卖 |
| QA-32 | 资金核对 | 可用与冻结变化、押金四态、买家付款、卖家入账、订单平台收入与收入流水相符 |
| QA-33 | Redis 切主／恢复 | 明确丢失与回退风险，恢复不得盲目覆盖新状态或自动制造结果 |

补充冻结模型验收：

| 编号 | 场景 | 预期外部结果 |
| --- | --- | --- |
| QA-34 | 同用户多场报名后处理其中一笔 | 只改变对应报名及押金，不能借用其他场次冻结金额 |
| QA-35 | 解冻、抵扣、违约扣除重复或冲突执行 | FROZEN 只能进入一个终态，钱包与流水同事务；冲突不能伪装成功 |
| QA-36 | 买家冻结或可用不足、任一流水写失败 | 整个结算回滚，不能部分付款或遗漏平台收入 |
| QA-37 | 正常成交与正尾款超时 | 直接扣冻结金额，不先解冻；分别记购买付款或违约扣款 |
| QA-38 | 平台收入重复投递 | 每订单对应业务键仅记录一次，金额与订单分账一致 |
| QA-39 | 不同场资金操作 | 不存在平台余额或子账户归集写热点；仍检查交叉用户钱包锁顺序 |
| QA-40 | 零尾款成交 | 购买付款金额等于完整成交价，可用变化 0、冻结减少对应押金 |
| QA-41 | Outbox 消息找不到任务或业务身份不符 | 不绕过任务核验动资金；正确任务与业务一起完成 |

未定业务边界如“首次等起拍价是否加时”要先确定，再增加明确验收预期。以上是待执行验收，不是测试通过报告。
