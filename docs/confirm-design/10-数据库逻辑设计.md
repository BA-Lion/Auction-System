# 10 数据库逻辑设计与冻结模型变更

所属基线：[v1.1](./README.md)。日期：2026-11-17。汇总已确认的九张表及当前冻结模型涉及的字段变化；不是最终建表 SQL。数据库产品、字段物理类型、外键、DDL 和未定索引仍需后续明确。

## DB-01 九张表的范围

保留 users、accounts、auction_items、auction_rounds、auction_registrations、auction_bids、auction_orders、fund_flows、fund_outbox。当前不另建平台账户表、归集表、押金冻结明细表、通用结算单表或投影状态表。每笔押金的占用由报名记录承担，平台收入由订单及流水表达。

## DB-02 用户与账户

users：id、username、password_hash、nickname、created_at、updated_at。username 唯一且非空；同一用户可买可卖，不另设买卖角色表。

accounts：保留账户 id、唯一用户关联、balance、created_at、updated_at，增加 frozen_balance。balance 只表示可用金额；同一用户一个钱包。

取消原来用于“用户／平台”区分的账户模型要求，不创建平台总账户或场次子账户，也不需要为子账户归集增加 status／closed_at。原 owner_type／owner_id 是否直接改为 user_id 在 DDL 中统一，不影响“只维护用户钱包”的已确认语义。

## DB-03 拍品与场次

| 表 | 已确认字段 |
| --- | --- |
| auction_items | id、seller_id、title、description、images、category_code、status、current_round_id、created_at、updated_at |
| auction_rounds | id、item_id、start_price、starts_at、ends_at、deadline_version、extension_count、status、current_price、current_bid_id、current_bidder_id、bid_version、winner_bid_id、winner_user_id、final_price、closed_at、created_at、updated_at |

拍品状态为待拍卖／待成交／已出售。场次正常状态为 WAITING → RUNNING → CLOSED，异常及人工暂停另行细化。达到截止但调度尚未关场时，可以仍为 RUNNING，Lua 仍按时间拒绝报价。重拍创建新场次。

当前报价字段为已同步运行状态，winner／final 字段为正式关场结果，不能被迟到旧报价修改。无人报价时相关报价和胜出字段可空，起拍价不能伪装成有效报价。

current_round_id 用于避免旧场任务误改新场拍品。场次没有冻结状态；是否尚有未处理押金通过报名表查询。

## DB-04 报名与出价

auction_registrations：id、round_id、user_id、deposit_amount、deposit_status、created_at、updated_at；UNIQUE(round_id, user_id)。deposit_amount 保留该报名实际冻结金额，不随之后配置变化。deposit_status 明确为 FROZEN、RELEASED、APPLIED、FORFEITED，转换见 05。旧“已缴纳待处理”改为 FROZEN，旧“已退还”在本模型对应 RELEASED。

报名记录与冻结金额变化、冻结流水同事务提交，失败报名不留下有效记录。不能仅凭账户冻结总额扣除某场押金。

auction_bids：bid_id 为主键、round_id、user_id、amount、bid_version、accepted_at、created_at。accepted_at 是 Redis 裁决时间，created_at 是落库记录时间。只存有效报价，不增加是否中拍或 RECEIVED／CONFIRMED 状态，不重复存 item_id。

已讨论索引：(round_id, bid_version) 和 (round_id, user_id, accepted_at, bid_id)；bid_version 暂不设唯一约束，bid_id 负责重投去重。

## DB-05 中拍订单

| 字段组 | 字段 |
| --- | --- |
| 身份 | id、round_id、buyer_id、seller_id |
| 固定金额 | deal_amount、deposit_amount、remaining_amount |
| 状态与付款 | status、expires_at、paid_at、closed_at |
| 分账 | settlement_type、settlement_base_amount、platform_rate_bps、platform_amount、seller_amount、settled_at |
| 通用时间 | created_at、updated_at |

round_id 唯一；通过场次关联拍品和胜出报价。索引方向为 (buyer_id, created_at, id)、(status, expires_at)。订单状态为待支付／已支付／超时关闭；分账类型为正常成交／流拍补偿，尚未结算时相应结果字段为空。

1000 基点 = 10%，5000 基点 = 50%。平台收入有专门流水并与 platform_amount 对应，不能因取消平台账户而删除分账信息。

正常或零尾款成交 paid_at = settled_at，closed_at 为空；正尾款超时 closed_at = settled_at，paid_at 为空。各自使用本次处理的统一时间值，事务失败不提交这些状态。

## DB-06 资金流水字段的变更边界

沿用 flow_id 主键、flow_type、amount、biz_id、created_at，以及 UNIQUE(flow_type, biz_id)。八类业务流水见 05：充值、冻结、解冻、购买付款、成交结算、押金扣除、流拍补偿、平台收入。

本次明确新增的逻辑信息为“可用余额变化”和“冻结金额变化”，必须能解释同一笔购买付款中两种资金来源。例如金额 230 元包含可用变化 −130、冻结变化 −100。

原 from_account_id／to_account_id 都关联真实 accounts 行的字段方案不再适合全部流水：冻结／解冻发生在同一钱包内部，平台收入没有平台账户行。正式 DDL 前需要确定用户归属、平台记账主体及交易对手如何表达，并明确用户钱包变化字段对平台收入记录的取值。不能使用不存在的虚构账户 ID 满足外键，也不能把平台收入挂到某个用户钱包。

这部分承认并记录字段调整需求，不把尚未讨论的新物理字段名称当成已确认。各流水业务含义、金额变化和幂等键已经明确，不需要新增一张平台账户表来解决表达问题。

## DB-07 资金任务字段

fund_outbox：id、round_id、user_id、event_type、biz_id、关联流水编号、payload、status、retry_count、last_attempt_at、last_error、completed_at、created_at、updated_at。UNIQUE(round_id, user_id)，任务为未中拍解冻或第一名超时处理。

status 表达待完成、SUCCESS、待投死信、已投死信；具体代码枚举与领取／租约字段待实现。已讨论扫描索引为 (status, last_attempt_at)，结合实际查询再校验。

消息 outbox_id 对应该表 id，biz_id 对应报名或订单。不能混用 outbox_id 与 flow_id。冻结设计下一条结算任务包含多条流水，原单 flow_id 字段如何与编号集合共存、是否改为载荷内按类型保存，列为待定；每条记录独立编号并具备业务去重是确定要求。

## DB-08 本轮替代内容

- 报名不再把可用余额转入平台，改为同用户可用转冻结。
- 未中拍不再由平台账户转账退款，改为该用户冻结转可用。
- 正常成交直接消耗冻结押金并扣尾款，购买付款流水记录完整成交价。
- 零尾款也记录购买付款；不产生零金额尾款转账。
- 正尾款超时直接扣冻结金额，买家支出、卖家补偿、平台收入都须记录。
- 不再创建、归集或关闭平台子账户；平台收入不需要实时平台余额。
- 去掉平台账户不代表不存在用户账户间的锁竞争，继续统一涉及的钱包加锁顺序。
