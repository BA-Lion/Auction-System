# 02 报名资格与出价裁决

所属基线：[v1.1](./README.md)。报名资金事务见 [05](./05-账户与有向流水.md)，消息转发见 [03](./03-报价消息与实时反馈.md)。

## BID-01 同槽数据边界

同一场次的资格、运行状态、榜单、pending 以及需要原子迁移的 inflight／failed 必须处于同一个 Redis Cluster 槽。以下只是 Key 命名示例：

| 示例 | 逻辑用途 |
| --- | --- |
| auction:{round-123}:state | 场次状态、价格、领先者、版本、截止、次数及同步标记 |
| auction:{round-123}:ranking | 本场 Top10 |
| auction:{round-123}:signup:user-88 | 用户 88 的本场资格，String |
| auction:{round-123}:pending | 已通过待发送报价，List |
| auction:{round-123}:inflight | 正在投递的一笔报价，List |
| auction:{round-123}:failed | 重试耗尽的完整报价，List |
| auction:{round-123}:deadline-sync-lock | 截止同步任务的锁 |

运行状态字段可以组织在 Hash，榜单可用 ZSet。榜单每个成员对应一笔有效报价，以 bid_id 区分。字段拆分、编码与截止索引在详细设计中确定。本基线冻结同槽边界及行为，不冻结这些物理细节。List 的元素是序列化字符串，不是内嵌 Redis Hash；完整事件的具体编码协议待定。

用户个人出价缓存仍按 user_id 路由，见 03。它不是 Lua 资格 Key，不需要和本场同槽，也不和本次报价做跨槽原子写入。

## BID-02 资格缓存的三态

开拍后仍允许报名，以本场最新有效截止为界。卖家不能报名自己拍品的场次。数据库完成报名、用户可用转冻结及冻结流水事务后，再将本场该用户资格写为字符串 1。

| GET 结果 | 含义 | 出价处理 |
| --- | --- | --- |
| 1 | 已报名且押金已冻结 | Lua 继续执行其他校验 |
| 0 | 最近明确回查无报名记录 | 拒绝本次未报名请求 |
| nil | 缓存未命中 | Lua 在任何报价写入之前返回资格未命中 |

缓存未命中由接入服务按 round_id + user_id 查询数据库报名记录。查到后回填 1，再沿用本次 bid_id 重新执行 Lua；第二次必须重新判断截止和最新价，不能沿用第一次的旧校验结果。

明确查无记录才以 NX 写短期负缓存 0，防止迟到的无记录结果覆盖已经写入的资格 1。NX 失败重新读取当前缓存。报名冻结事务成功后写 1 覆盖已有 0。数据库超时或异常不能转成“未报名”或写负缓存。

正资格缓存覆盖竞价期间；负缓存实际 TTL 未定，旧稿举例的 60 秒不是强制参数。同用户同场缓存回查合并可作为实现优化，不是已经确定的机制。

## BID-03 调用前与时间语义

1. 用户提交明确金额；不采用服务端基于不断变化的最高价替用户任意增加预算的按钮语义。
2. 接入服务验证身份、参数和入口限流，为新提交生成 bid_id。
3. 身份取自认证上下文，调用本场 Lua；所需 Key 显式提供，保持同槽。
4. 金额使用整数分并限制数值范围，避免 Lua 和 ZSet 数值精度导致比较错误；雪花等长编号作为字符串处理。
5. 有效时点以 Redis Lua 实际执行裁决时读取的 Redis 时间为准。客户端提交时间、网关接收时间可以留作排查，不能覆盖该规则。

因此截止前到达网关但排队到截止后才执行的请求仍被拒绝。网关可以预检，最终收录由 Lua 决定。

## BID-04 第一次写入前完成全部校验

| 次序 | 检查内容 | 不通过时 |
| --- | --- | --- |
| 1 | 参数、Key 类型、必要配置与状态是否存在 | 返回异常，不用空状态自动开一场 |
| 2 | 本场该用户资格 | 0 拒绝；nil 走回查；1 继续 |
| 3 | 场次允许竞价、达到开始时间 | 未开始、关闭或暂停时拒绝 |
| 4 | Redis 当前时间小于本场截止时间 | 达到或超过截止即拒绝 |
| 5 | 报价满足起拍及最新最高价规则 | 价格不足拒绝 |
| 6 | 待发容量、适用的积压限流状态 | 繁忙拒绝，不先更新价格 |

首次有效报价至少达到起拍价。已有有效报价时，下一笔至少高于当前最高价 1 分。当前领先者也可以继续出价，同样接受价格、资格和截止校验。

pending + inflight 的数量作为本队列待发容量检查口径，阈值待定。Kafka lag、failed 等后台信号如何转成入口控制见 08。

## BID-05 计算、写入与原子边界

校验完成后先准备新状态及完整事件，包括可能的加时，再进行写入：

1. 更新本场最高价、领先 user_id、领先 bid_id 和状态版本。
2. 按金额降序保留本场前十笔有效报价，同一用户的多笔报价各占一行。
3. 符合加时规则时更新截止时间、加时次数、截止版本，并置待同步标记。
4. LPUSH pending 放入完整报价事件。
5. 返回本次裁决结果及最新状态。

以上在同一个短 Lua 内完成，不调用数据库、Kafka、ES，不在脚本中等待截止数据库同步锁。普通未加时的报价不能清除先前留下的待同步标记。

Lua 原子性指执行期间不与其他客户端命令交错，不代表运行错误后自动回滚此前写入。因此参数、类型、容量、事件序列化等可预检工作尽量放在第一次写入前；脚本运行错误或响应丢失按结果未知核对，不能当作明确拒绝然后盲目重放。

## BID-06 事件与接口语义

以下为必须保留的逻辑信息，最终字段名及编码在接口设计中确定：

| 信息组 | 内容 |
| --- | --- |
| 身份 | bid_id、round_id、lot_id、user_id |
| 报价 | 金额、Redis 裁决时间 |
| 排序与状态 | 状态版本、领先报价身份；有能力区分同场迟到旧状态 |
| 截止 | 裁决后的截止时间与版本、是否加时、加时次数 |

pending 保存完整事件，不只保存 bid_id。只有裁决成功的报价进入有效报价链路；拒绝请求不冒充有效出价记录，其诊断日志是否保存及保存多久另定。

成功回执至少能表达：已通过、bid_id、裁决时的最高价和领先者、状态版本、截止时间与版本、是否加时、是否最后一次加时、是否有截止待同步。领先只是该次裁决时的事实，不保证用户收到回执时仍领先。

失败区分未开始、未报名、已截止、价格不足、繁忙和状态异常；可附当前价或截止帮助展示。明确截止拒绝直接反馈给用户，不另行请求已取消的汇总端。结果未知不能伪装成明确失败。

## BID-07 回执后的独立工作

Lua 成功即可返回，不等待 Kafka、数据库或 ES。接入服务另行写个人 ACCEPTED 回执、发布场次变化，并在需要时尝试启动截止同步。某一后续动作失败不撤销已经成功的裁决，补偿方式由对应模块定义。

用户暂时不能以原 bid_id 重试，入口不承诺点击级幂等。资格未命中时用原 bid_id 再执行是安全分支，因为第一次尚未写入；这与出价执行结果未知后的重试不同。报价转发重试始终复用已生成的身份，不能生成新报价。

Redis 开启 AOF everysec。已通过并不等于已刷盘、已复制或已进 Kafka，机器故障及切主可能损失最新报价。恢复和核对边界见 08。
