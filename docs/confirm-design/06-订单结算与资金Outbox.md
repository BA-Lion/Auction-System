# 06 订单、结算与资金 Outbox

所属基线：[v1.1](./README.md)。更新日期：2026-11-17。正式结果来自 [04](./04-加时截止同步与关场.md)，钱包与流水语义见 [05](./05-账户与有向流水.md)。

## PAY-01 建单与任务

正常结拍后按 round_id 唯一建单，固定买家、卖家、成交价 P、该报名实际冻结押金 D、尾款 R = P − D 和 expires_at。拍品及胜出报价通过场次关联。付款窗口为竞拍结束后两小时，不因消费迟到重新延长。

正式结果重复交接不能重复建单。无有效报价不建订单，本场未中拍报名的押金通过解冻任务收尾。异常金额不以截断负尾款等办法掩盖。

- 未中拍者产生押金解冻 Outbox，旧文中的“押金退款”在当前模型中均表示解冻回可用余额。
- 第一名押金继续保持 FROZEN，正尾款订单待支付，并登记订单到期 ZSet。
- 零尾款立即走正常成交分支。

正式结果、订单与批量解冻任务的可靠交接及失败补建仍待设计，不假定它们组成一个跨 Redis 与数据库的原子事务，也不要求整场所有用户资金在一个大事务处理。

## PAY-02 正常成交写库事务

付款请求先做身份认证和参数检查。金额读取订单固定值，不能由客户端金额决定。数据库事务内顺序如下：

1. 锁定订单，核对买家身份及订单状态。已支付返回原结果；已超时关闭拒绝；待支付继续。
2. 锁定本场中拍买家的报名记录，确认 deposit_status = FROZEN，报名归属正确，deposit_amount 与订单 D 一致。
3. 对涉及的买家、卖家账户 ID 去重并统一升序锁定。业务行及 Outbox 的完整锁顺序在实现中进一步统一。
4. 在资金写入前核验正尾款付款未到期，校验 P = D + R、可用余额足够支付 R、冻结余额足够消耗 D；计算本单分账。
5. 一次条件更新同时令买家 balance −R、frozen_balance −D。不能先解冻 D 再另行付款。
6. 增加卖家 balance，金额为 P 扣除平台 10% 收入后的实际值；报名押金由 FROZEN 改为 APPLIED。
7. 写三条不同类型流水：买家购买付款 P（可用 −R／冻结 −D）、卖家成交结算 S、平台收入 F。各有独立 flow_id 和对应业务唯一键。
8. 保存订单分账基数、费率、卖家与平台金额，订单改已支付；拍品仍关联本场且状态符合预期时改已出售。关联异常不能在掩盖冲突的情况下继续结算。
9. paid_at 与 settled_at 使用同一本次处理时间，提交全部写入。

任一步失败，钱包、押金状态、三条流水、订单与拍品修改一并回滚。流水唯一键冲突不能忽略后继续扣款，应回滚后核对已提交结果。卖家在付款成功时立即获得钱包入账，不等待收货。

正常主动付款涉及 accounts、auction_registrations、fund_flows、auction_orders、auction_items 五张表。没有对应资金任务时，不需要凭空创建或更新 Outbox。提交之后再做缓存、通知等外部动作，其失败不能改称数据库付款失败。

示例 P=230 元、D=100 元、R=130 元：买家冻结 −100、可用 −130；卖家可用 +207；平台收入流水 23。平台没有余额行，不进行子账户或归集操作。

## PAY-03 零尾款与时间字段

R = 0 时仍执行正常成交：消耗冻结 D，报名改 APPLIED，卖家入账，平台收入记账，订单已支付，拍品已出售。可用余额不再扣款。

零尾款也要记录购买付款流水，因为冻结押金实际被用于支付完整成交价 P。该流水不是零金额尾款记录，而是金额 P、可用变化 0、冻结变化 −D。旧版“零尾款不写购买付款流水”的解释不再适用。

异常遗留待支付零尾款订单，由超时消费者调用同一幂等成交流程兜底，同时在事务中完成对应 Outbox。不能记录成违约扣款或流拍补偿。建单直接成交与兜底入口共用订单和流水业务唯一约束。

| 结果 | paid_at | closed_at | settled_at |
| --- | --- | --- | --- |
| 正常付款、零尾款成交 | 本次处理时间 | 空 | 与 paid_at 相同 |
| 正尾款超时补偿 | 空 | 本次处理时间 | 与 closed_at 相同 |
| 事务回滚 | 不提交本次赋值 | 不提交本次赋值 | 不提交本次赋值 |

时间字段表示相应业务完成记录，不声称应用取得时间戳的瞬间就是数据库物理提交时刻。

## PAY-04 未中拍解冻事务

消费者按 outbox_id 查任务，核对报名、用户、场次及押金金额，取得本报名和钱包处理权。确认该报名应解冻且仍为 FROZEN 后，在同一事务执行：

1. 有条件扣减该用户 frozen_balance 的 D，并增加 balance 的 D。
2. 报名状态设 RELEASED。
3. 写押金解冻流水，金额 D、可用 +D、冻结 −D，业务编号为报名 ID。
4. 对应 Outbox 设 SUCCESS 并记录完成时间，一起提交。

已完成 RELEASED 的重复任务核对原结果后幂等结束。若押金已经 APPLIED／FORFEITED，则属于与解冻请求冲突的分支，不能再增加可用余额或无条件冒充解冻成功。胜出者冻结押金不能被退款任务释放。

## PAY-05 超时发现

数据库订单保存 expires_at；待支付订单建单后，将 order_id 按到期时间写入 Redis ZSet。后台初始周期约每分钟扫描，先可靠写超时 Outbox，再清理对应成员。

数据库每天小批补扫到期仍待支付订单，覆盖 ZSet 漏写、丢失或未处理，两条发现路径共用任务唯一键。付款接口在事务中检查截止，不能因为扫描尚未运行就允许过期付款。

该 ZSet 仅用于订单付款到期调度，不是全局竞拍截止权威。扫描批大小、领取和接管机制仍待详细设计。

## PAY-06 超时消费者及补偿事务

消息到达后重新锁定并检查订单，不能相信消息创建时的旧状态。付款和超时分支竞争同一订单处理权。

| 当前情况 | 处理 |
| --- | --- |
| 已支付／已经完成超时关单 | 核对可确定的既有结果，任务幂等完成，不再动资金 |
| 待支付但未到期 | 不关单、不记假成功，保留到期后处理机会 |
| 待支付、到期、零尾款 | 执行 PAY-03 正常成交兜底 |
| 待支付、到期、正尾款 | 执行下述违约扣款和补偿 |

正尾款补偿事务：锁定订单与本报名，核验押金仍 FROZEN；钱包按统一顺序加锁；买家 frozen_balance −D，balance 不变；卖家 balance 增加 D 扣除平台 50% 收入后的金额；报名改 FORFEITED。

同事务写买家押金扣除、卖家流拍补偿、平台收入三条流水；保存订单补偿分账信息，订单超时关闭，closed_at 与 settled_at 同值、paid_at 为空；按场次关联检查拍品状态，防止旧任务影响重拍场次；对应 Outbox SUCCESS，一起提交。

例如 D=100 元：买家冻结 −100，卖家可用 +50，平台收入 50。不扣尾款、不把押金返还可用余额、不先执行解冻。第一名违约不候补，拍品完成流拍处理后恢复待拍卖，重拍新建场次。

订单不存在、押金归属或状态冲突等未知结果进入异常核对，不能直接标 SUCCESS。提前到达消息的再次调度方式仍待实现。

## OUT-01 任务身份、消息匹配与流水编号

fund_outbox 是数据库资金任务表，与 Redis 报价 pending 不同。当前任务类型为未中拍押金解冻、订单超时处理；round_id + user_id 唯一，超时 user_id 指买家，卖家在业务载荷中。这两类任务当前互斥，不能把该唯一键用于所有未来事件或 ES 同步任务。

Kafka 消息必须携带 outbox_id，对应 fund_outbox.id；业务编号定位报名或订单，流水编号定位资金记录，三者职责不同。示例 outbox_id=9001、order_id=123：消费者查任务 9001，核对类型及其 biz_id 确为订单 123，在处理订单的事务中更新任务 9001。找不到任务或身份冲突时不能绕过校验继续扣款。

任务至少保存 id、round_id、user_id、event_type、biz_id、业务载荷、关联流水编号、状态、retry_count、last_attempt_at、last_error、completed_at 和创建修改时间。重投保持任务身份和原业务内容。

冻结模型使一条超时结算任务产生三条资金记录。旧稿一个 flow_id 代表全部资金效果的承载方式不够，每条流水必须独立编号，并以 flow_type + biz_id 去重。任务创建时预生成并持久化所需流水编号的原则保留，具体编号集合格式、正常零尾款兜底的编号绑定及字段承载方式列为待细化，不默认三条记录共用一个主键。

## OUT-02 业务成功及事务位置

Broker ACK 只代表投递得到确认，Outbox SUCCESS 表示业务事务完成。对于解冻、正尾款补偿、零尾款兜底，钱包、流水、报名和相关订单状态与任务 SUCCESS 一起提交。业务失败则成功标记一并回滚，供后台继续补发。

正常付款不需要更新尚未创建的超时任务。若超时消息后来到达并发现订单已支付，消费者只幂等完成该任务。已完成超时订单同理。任务已投死信但后续获得可核验的业务成功时，不能用迟到失败写覆盖 SUCCESS。

## OUT-03 十分钟补发与五次预算

普通转发器分批领取新任务，首发 retry_count=0。补发查询未 SUCCESS、距最近尝试超过 10 分钟且 retry_count<5 的任务；没有尝试时间的长期未首发任务可用创建时间判断。

每次重发前原子领取、计数加一并记录尝试时间，再发送原消息。第 5 次补发仍有真实发送机会；再经过一个 10 分钟观察窗口未成功，进入死信流程。待投死信与已投死信分开，收到死信 ACK 后才标记投递完成。迟到业务 SUCCESS 优先。

计数保存在数据库，可跨重启恢复，与报价转发器内存三次重试无关。领取后退出可能消耗预算但未发送，租约恢复和计数审计仍待细化。人工重放保持原任务和已绑定的流水身份，不重复冻结、解冻、扣款、卖家入账或记录平台收入。

## OUT-04 事务写入汇总

| 分支 | 同一数据库事务内至少包含 |
| --- | --- |
| 报名 | 用户可用转冻结、唯一报名 FROZEN、冻结流水 |
| 主动正常付款 | 买家冻结和尾款扣除、卖家入账、三类结算流水、报名 APPLIED、订单分账及已支付、拍品已出售 |
| 未中拍解冻 | 用户冻结转可用、解冻流水、报名 RELEASED、Outbox SUCCESS |
| 正尾款超时 | 买家冻结扣除、卖家补偿、三类补偿流水、报名 FORFEITED、关单与分账、拍品收尾、Outbox SUCCESS |
| 零尾款超时兜底 | 与正常成交相同的冻结消耗和三类流水、报名 APPLIED、订单及拍品状态、Outbox SUCCESS |

不把 Redis、Kafka、ES 或 WebSocket 调用放入这些数据库事务的原子性承诺内。
