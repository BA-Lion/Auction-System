# 04 加时、截止同步与关场

所属基线：[v1.1](./README.md)。本文件采用单场同槽裁决，不再使用多个出价分片之间的加时协议。

## END-01 截止权威与时点

本场 Redis 维护运行截止时间，数据库场次表维护持久化截止时间。不额外设置跨场次的全局权威截止时间。调度索引可以帮助发现候选任务，但不能取代本场当前截止。

出价 Lua 读取所在 Redis 的时间，当前时间达到或超过截止时间时拒绝；网关接收时间不能覆盖这个结果。正常运行中本场所有裁决在同一主节点执行，无需比较多个出价分片的时钟。Redis 切主后的时钟偏差与状态恢复仍属于待验证的故障边界，不能理解成 Cluster 保证所有节点时钟一致。

## END-02 加时规则

| 规则 | 已确定内容 |
| --- | --- |
| 时间窗口 | 当前截止前最后 10 秒 |
| 触发事件 | 窗口内接受的有效报价抬高最高金额 |
| 单次延长 | 在原截止时间基础上加 30 秒 |
| 次数上限 | 单场最多 5 次 |
| 最后一次通知 | 第 5 次回执及广播明确标记最后一次加时 |
| 到达上限 | 仍按最新截止正常受理有效报价，但不再延长 |

价格校验和加时判断在同一个出价 Lua 内，成功加时同时更新截止、截止版本、次数和待同步标记。重复通知、重发旧事件、同价或没有新报价的读取都不能增加加时次数。

首次报价恰好等于起拍价是否触发加时仍未确认，不能把本文件的“抬高最高金额”解释为已经决定了该边界。窗口起点的比较符号与时间精度在详细设计中统一。

## END-03 截止同步标记和多实例锁

多实例接入时，Lua 返回待同步信息，接入服务尝试取得本场截止同步锁。没拿到的请求直接结束，不等待持有者。拿到锁的实例启动后台任务，不让数据库更新阻塞本次报价反馈。

以下为同步正确性要求：

1. 每次真实加时增加截止版本，并设置待同步标记。未加时报价不能清除该标记。
2. 持锁任务读取最新 Redis 截止及版本后，按数据库版本条件更新场次截止；较旧结果不能覆盖较新结果。
3. 数据库提交成功后，再检查当前锁归属及 Redis 截止版本。
4. 若仍是已同步的版本，在同一原子检查中清除标记并释放自己的锁。
5. 若期间又有加时，保留标记，继续同步最新版本，不能清掉新任务。
6. 同步失败不把标记清掉；进程退出、锁过期、异步任务未启动等情况由后台补扫接管。

锁只减少正常情况下重复同步，不能单独保证永久只有一个任务；锁过期后旧任务可能仍执行。因此数据库版本条件与锁归属检查必须同时存在。失去锁的旧任务不能删除新任务的锁或标记。

同步任务使用新鲜截止，不把第一次收到的旧值当作后续固定值。数据库已存在更高版本时，不能强行改回旧值；特别是切主造成 Redis 回退的情况，需进入恢复核对，具体策略待定。

## END-04 最后一笔加时也必须能落库

不能仅依赖下一次报价发现待同步标记。场次尾盘可能再无请求，因此后台需要发现未完成同步并补做。待同步场次如何索引、扫描频率、锁 TTL／续约、重试次数与退避参数暂未冻结。

同场 Lua 已更新的新截止可以先用于出价与展示，不等待数据库同步。旧架构“所有 Redis 分片都确认新截止后才广播”的条件已经取消。通知仍遵循先更新运行状态、后广播，可靠性见 03。

## END-05 到期与关场竞争

后台任务触发到期检查，最终在本场 Redis 原子边界内核对当前场次状态、时间和最新截止。

| 原子执行顺序 | 必须表现 |
| --- | --- |
| 有效报价先执行并延长截止，关场后执行 | 关场读到新截止，不按旧截止关闭 |
| 已到期关场先完成关闭，报价后执行 | 报价读到关闭状态并拒绝 |
| 数据库截止落后，后台提早发现候选 | 仅触发核验，不能直接据旧时间建成交订单 |
| 重复到期任务 | 不能重复确定不同赢家或重复生成业务效果 |

不再进行 N+1 汇总，不收集多个分片的最终快照，也不因“截止前已收录但稍后才汇总到”重新开放。旧稿截止后最多等待一分钟的规则已经失效，新调度周期与异常阈值待定。

## END-06 正式结果与资金交接

正常关闭后，必须固定正式中拍结果，包括 round_id、胜出 bid_id、买家与成交金额；保留能够关联本场状态和截止版本的证据。无有效报价时不生成中拍订单。

正式结果驱动同场唯一建单、未中拍参与者押金解冻任务，以及第一名后续付款／超时处理。订单金额使用固定结果，不在用户付款时重新查询变化中的榜单计算成交金额。

关场重复调用应返回同一已固定结果。采用关场 Lua 固定快照是当前建议；正式结果如何可靠从 Redis 交接到数据库、与建单和批量解冻任务如何协同、进程中途退出如何补建，尚未确定完整实现。不能把“Redis 已关闭”和“数据库已建完全部订单及解冻任务”宣称为一个跨系统事务。

没有报价但有报名时，需要把对应冻结押金解冻回用户可用余额并完成拍品状态收尾；这一分支的具体落库及任务生成流程尚待细化。

## END-07 异常处理边界

单场运行状态或正式结果不可核对时，保留证据并交后台处理，不能以 ES 价格、客户端时间或缓存榜单随意补成正式成交。用户允许管理员及运维接管，但自动处理、暂停或恢复的具体条件未全部确定。

旧版“加时同步某个出价分片连续失败后如何处置”的分支随同场多分片架构取消，不移植成当前 Redis 到数据库同步的五次重试规则。
