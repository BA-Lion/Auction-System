## 3. 已选主线

1. 产品侧重点是多场次并行、同场并发正确性和及时反馈，不假设单商品存在海量有效报价。
2. NGINX 作为当前阶段入口反向代理与负载均衡；后面部署多个业务与 WebSocket 实例。
3. 同一场次的裁决状态、资格和报价待发链路使用相同 Redis Cluster 哈希槽；不同场次可以分布到不同主节点。
4. 一个出价 Lua 完成资格、场次、时间、价格和容量校验，再更新最高价、榜单、必要的加时及完整 pending 事件。
5. Lua 成功后快速回复；Redis 采用 AOF everysec，接受报价进入 Kafka 前仍存在丢失窗口的取舍。
6. 报价通过 pending → 单容量 inflight → Kafka 转发；Broker ACK 后清理，重试耗尽进入 failed，重发沿用原 bid_id。
7. 个人“已确认”表示确认消费组从 Kafka 读到了报价；数据库持久化由另一消费组独立推进。
8. 加时在本场 Lua 内即时决定，截止时间异步同步数据库；关场以本场 Redis 当前截止与状态重新核验。
9. 数据库是权威持久化存储，承担订单、余额、流水与资金任务的事务；ES 只是可重建的列表查询派生数据。
10. ES 列表允许延迟，通过 PIT + search_after 保持一次翻页会话的视图稳定；五分钟是待验证参数。
11. 押金按起拍价从用户可用余额转为冻结金额；未中拍解冻，正常成交直接消耗冻结押金并付尾款，正尾款超时直接扣冻结押金作补偿。正常成交平台收入 10%，超时平台收入 50%，不候补。
12. 取消平台总余额与场次子账户。平台收入写订单和独立流水；押金状态在报名表，FROZEN 只能转 RELEASED／APPLIED／FORFEITED。
13. 单笔历史报价异常默认隔离、记录、告警和补发，不因任意缺口自动停掉整个系统；资金与最终结果异常不能按普通历史明细问题忽略。

## 5. 本基线不承诺的内容

尚无确定的 QPS、P99、最大连接数或可用性指标，不承诺 Redis 已接收数据绝不丢失，也不承诺能发现所有无证据的数据丢失。九张表的逻辑字段见 10；流水主体表达、多流水编号承载、最终 SQL 类型和约束等未定细节仍明确保留。本文不替用户决定未讨论的规则、服务框架、Kafka 参数或自动恢复算法。未定事项集中在 09，不阻止已经明确的模块继续开展详细设计。
