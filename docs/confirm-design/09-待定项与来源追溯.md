# 09 待定项与来源追溯

所属基线：[v1.1](./README.md)。本文件把确定的边界与未选的实现分开，防止后续开发把建议升级为已确认规则。

## OPEN-01 尚未决定的业务边界

| 编号 | 待定内容 | 已经确定的边界 |
| --- | --- | --- |
| O-01 | 榜单按用户还是按单笔报价；同值排序规则 | 保留 Top10，用户通过榜单判断领先 |
| O-02 | 最低加价阶梯、领先者能否再次出价、是否另设同价规则 | 有效报价先满足起拍价，已有报价时严格高于当前最高价 |
| O-03 | 首次恰好等于起拍价是否加时；10 秒起点边界精度 | 最后 10 秒有效涨价触发，+30 秒，最多 5 次 |
| O-04 | 暂停、异常、恢复及正式结果证据冲突时的人工操作 | 单条历史异常不自动停整个系统，不能伪造可核验成交结果 |
| O-05 | 无报价但有报名时的完整关场收尾 | 不建中拍订单，需要解冻押金和拍品收尾 |
| O-06 | PIT 五分钟的空闲、续期、总寿命口径；跳页和总数体验 | ES 列表允许延迟，同查询视图稳定，失效后重新查询 |

本基线没有加入自动代理出价、自动候补、撤销报价、提现、外部支付渠道、物流收货或退款售后规则。

## TRACE-02 已废止的设计汇总

1. 同一场按 bid_id 分到多 Redis 分片，仅按局部最高价筛选。
2. N+1 汇总各分片前十，以汇总端发现变化决定加时。
3. 对同场多个 Redis 写入同一截止并等待全部确认。
4. 截止后收齐各分片到期快照，最多等一分钟，或发现晚汇总报价后重新开放。
5. 报名资格按 user_id 分槽，出价 Lua 无法同槽检查。
6. 把 Kafka offset 必须连续、任何版本缺口立即停拍作为新系统前提。
7. 把最初“复制日志先确认才回复”视为现行规则；现行为 Lua 成功回复、AOF everysec。
8. 报名直接转入平台余额、创建场次子账户、归集到平台总账户及关闭子账户的路线。
9. 购买付款只记录尾款、零尾款不记购买付款、平台收入不单独记流水。
10. 把冻结状态放在场次表，或要求成交和违约必须先解冻再扣款。

仍然保留按 user_id 组织个人回执，不能把第 5 条误读成所有用户缓存都改按场次路由。
