# 03 报价消息与实时反馈

所属基线：[v1.1](./README.md)。本文件的 Redis 报价队列与 [06](./06-订单结算与资金Outbox.md) 的数据库资金 Outbox 是不同链路。

## MSG-01 队列所有权

pending、inflight、failed 归稳定逻辑队列单元所有，而不是归某个临时进程所有。进程重启或换实例接管时，继续处理原队列。

每个队列单元只有一个活跃转发所有者，inflight 容量一笔。不同队列可以并行。新的单场同槽方案要求本场写入与领取、异常迁移保持同槽；每场单独队列还是多个场次放入同槽业务桶、怎样调度大量队列，尚未冻结。不能机械继承旧方案“每台物理 Redis 一个线程”的配置。

容量一笔是协议约束，List 本身不会自动限制长度；所有权、空槽检查及领取方式必须共同保证它。常驻线程数、连接复用、任务领取和故障接管由详细设计确定。

## MSG-02 正常转发

1. Lua 用 LPUSH 写 pending，领取从右侧取最老事件，形成左进右出。
2. 转发器启动先检查遗留 inflight，有记录先处理，不先领新记录。
3. inflight 为空时，原子地从 pending 取走事件并移入 inflight，不能分成先弹出再另一次写入。
4. 同槽 BLMOVE 是已讨论的领取办法；旧例 RIGHT → LEFT，空队列可阻塞等待。它不能单独解决双所有者或容量约束。
5. pending 无消息时等待，新报价入队后恢复工作；可持续搬运到待处理队列为空，无需每笔创建新转发器。
6. 向 Kafka 发送当前完整事件，收到 Broker 写入 ACK 后，清理对应 inflight，再领取下一笔。

清理必须针对正在处理的对应记录，不能让迟到 ACK 清掉后来接管者的新记录。ACK 丢失或进程退出可能造成重复发送，所以“发完才删”保障可重投，不等于恰好投递一次。

## MSG-03 失败、重试与补发

| 项目 | 规则 |
| --- | --- |
| 一轮发送 | 包括 Kafka 客户端内部在该轮进行的重试 |
| 应用重试预算 | 首发未确认后最多再发 3 轮 |
| 身份与内容 | 每轮使用原 bid_id、原事件内容 |
| 计数位置 | 转发器内存；换下一笔清零，重启或接管重新计数 |
| 超时但发送未结束 | 先界定本轮结束，避免无控制地叠加发送 |
| 重试耗尽 | 将完整事件从 inflight 原子转入同槽 failed，继续后续记录 |
| 明确单条格式错误 | 可直接隔离并记录原因 |
| Kafka 整体不可用 | 整体退避、告警，避免逐笔耗尽预算搬空到 failed |

failed 按逻辑队列／分片组织以保证同槽迁移，后台集中统计局部及总量。保留原始身份、载荷与排查信息。后续补发沿用原 bid_id，不重新作为新出价裁决，也不能重复触发加时。自动或人工补发入口、权限与领取方式尚待细化。

报价进入 failed 时仍可能实际已到达 Kafka，因此个人展示可以是待核对，不能直接断言永久失败。迟到确认优先于先前的待核对状态。

## MSG-04 Kafka 与数据库消费

当前保留按 bid_id 选择 Kafka partition 的方案；若后续明确需要同场 Kafka 顺序，必须另做决策。Redis 同场串行裁决不意味着不同 partition 的消费者观察顺序一致。

- 报价明细以 bid_id 唯一约束幂等保存，数据库事务成功后才推进消费进度。
- 同身份重投不得重复插入业务明细。相同 bid_id 却内容不同应保存冲突证据并告警，不能无条件视为正常重复。
- 若同时维护数据库场次当前值，只允许较新的有效状态更新，迟到旧报价仍可保存明细，但不能覆盖新最高价或新截止。
- Kafka offset 用于消费进度，不要求对应用可见消息严格逐个加一，不能以数字不连续直接认定业务记录丢失。
- 不把任何一笔历史缺失自动转化为全场版本断裂而永久阻塞竞拍；缺失检测和修复旁路推进。
- 若消费端要跳过持续失败记录，必须先可靠保存原事件和失败信息；消费失败重试、隔离及 offset 提交的具体协议仍待详细设计，不能直接套用转发器的三次预算。

是否另设 inbox、数据库进度表及具体事务范围未冻结。目标是可重投、业务幂等、能查明异常，不承诺跨 Redis、Kafka 和数据库的全局原子事务。

## MSG-05 个人报价缓存与反馈状态

个人记录按 user_id 路由，便于直接查登录用户在本场的所有近期出价，无需遍历所有场次写分片。可以使用 ZSet 做最近记录索引、Hash 存按 bid_id 对应的金额和状态；最终物理结构、TTL 与历史分页接口待定。

| 状态／事实 | 触发 | 意义 |
| --- | --- | --- |
| RECEIVED／已接收 | Lua 成功后由接入服务另写个人缓存 | Redis 裁决及待发入队成功 |
| CONFIRMED／已确认 | 独立 Kafka 确认消费组读到完整报价后更新 | 报价已进入 Kafka，不等于另一消费组已落库 |
| 待核对 | 响应或投递结果未知、报价被异常隔离 | 等待确认或补发，不能覆盖已确认 |
| 已落库 | 数据库报价事务提交 | 独立事实；是否直接展示该状态由接口设计确定 |

个人缓存写入独立于报价 Lua，失败不回滚竞价结果。刷新时可以看到 RECEIVED，不必等数据库查询。若刚写入后刷新尚查不到，确认消费者可补建缺失记录。迟到的 RECEIVED 和异常通知不能把 CONFIRMED 降级。

HTTP 回执丢失时，用户可查询个人近期记录；当前没有允许用户携原 bid_id 重提出价的接口承诺。

## MSG-06 实时推送与重连

场次频道广播最高价、榜单、截止变化及最后一次加时标志；个人频道按认证用户投递报价确认。用户通过榜单判断领先，不为每人维护一个强一致的“永远领先”状态。

先更新对应可查询状态，再发通知。客户端以展示版本合并快照和推送、忽略迟到旧状态；个人记录按 bid_id 合并并保持确认单向推进。断线重连需要补取场次快照和个人记录，订阅与快照交接须覆盖竞态。

WebSocket 请求可经 NGINX 分配给不同实例。跨实例分发不能仅在接收出价的那一实例广播。Redis Pub/Sub 是历史讨论中的候选传输，不承诺通知持久化；最终通知来源、重连补偿、频率及合并策略尚待设计。

实时推送不等待数据库或 ES，不再固定每秒跨 Redis 分片拉取并合并榜单。单次 Lua 原子裁决也不意味着网络推送零延迟。
