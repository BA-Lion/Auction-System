# 05 账户、押金冻结与资金流水

所属基线：[v1.1](./README.md)。更新日期：2026-11-17。订单结算事务和异步任务见 [06](./06-订单结算与资金Outbox.md)，逻辑字段见 [10](./10-数据库逻辑设计.md)。

## FUND-01 用户钱包与金额

当前采用用户内部钱包：balance 表示可用余额，frozen_balance 表示冻结金额，均为整数分。冻结金额仍属于该用户，但不能用于其他付款。竞拍者、买家、卖家是同一用户在不同业务中的角色。

不维护平台总余额账户或场次平台子账户，不创建归集、关闭、删除平台账户的流程。平台收入以订单分账字段和专门的平台收入流水记录，不在每笔交易中更新共享余额行。

报名、解冻、购买付款、卖家入账和补偿是本地数据库账务操作，不调用外部支付接口。面试项目可提供模拟充值入口，依据稳定业务编号幂等入账；模拟接口协议仍待实现，真实支付渠道、提现与外部打款不在当前范围内。

数据库内检查余额条件，并将钱包变化、流水和业务状态一起提交。可用余额、冻结金额及总资产不能混为同一个字段，不使用客户端传来的金额决定实际扣款。

## FUND-02 每笔押金的归属与状态

冻结状态放在 auction_registrations.deposit_status。每个 round_id + user_id 唯一，deposit_amount 固定本场实际冻结的押金；当前冻结额度等于该场起拍价。用户 frozen_balance 是全部未处理押金的总额，报名记录负责把其中每一笔关联到具体场次。

| 状态 | 业务含义 | 本次钱包变化，D 为该笔押金 |
| --- | --- | --- |
| FROZEN | 报名成功，押金占用中 | 报名时 balance −D，frozen_balance +D |
| RELEASED | 未中拍，押金已解冻 | frozen_balance −D，balance +D |
| APPLIED | 押金已用于正常成交 | frozen_balance −D，同时按订单另扣可用尾款 |
| FORFEITED | 正尾款超时，押金已用于补偿和平台收入 | frozen_balance −D，不返还可用余额 |

```text
报名成功 → FROZEN
             ├─ 未中拍解冻 → RELEASED
             ├─ 正常成交   → APPLIED
             └─ 超时扣除   → FORFEITED
```

后三个状态互斥且为该笔押金终态。冻结和解冻不需要成对发生：成交、超时直接消耗冻结金额，不先解冻再扣款。不能仅凭总冻结金额充足就支出，必须核对本场报名仍为 FROZEN，防止误用其他场次押金。

场次仍使用 WAITING → RUNNING → CLOSED，没有场次级冻结状态。CLOSED 不等于所有报名押金都已处理完。是否还存在 FROZEN 报名记录可用于检查本场押金收尾；资金是否全部一致仍需结合订单、任务和流水核对。

## FUND-03 报名冻结与资格缓存

报名事务：读取本场起拍价，插入唯一报名记录，检查并把可用金额转入冻结金额，记录冻结流水，一起提交。余额不足、唯一约束冲突或流水失败都不能留下部分冻结。数据库事务成功后再写本场 Redis 资格 1。

重复报名查询原记录，不再次冻结；可以补写资格缓存。数据库提交后缓存写失败不表示报名失败，出价资格未命中时由数据库回查补建。正负缓存与同槽 Lua 的规则见 02。

资格 1 表示报名押金已按当前规则冻结成功；是否还能出价同时由场次状态、时间等裁决。解冻／结算不把场次重新变成可竞价。

## FUND-04 流水类型、金额与归属

每条资金变动或平台收入记录分配雪花 flow_id。流水要能表达所属用户或平台记账主体、业务类型、业务编号、金额、钱包可用变化和冻结变化，以及必要的交易对手关联。平台是收入记账主体，不对应 accounts 中一条真实余额账户。

| 类型 | 金额含义 | 可用变化 | 冻结变化 | biz_id |
| --- | --- | --- | --- | --- |
| 充值 | 确认充值金额 C | 用户 +C | 0 | 稳定充值业务编号 |
| 押金冻结 | 本场押金 D | 竞拍者 −D | +D | 报名记录 ID |
| 押金解冻 | 本场押金 D | 竞拍者 +D | −D | 报名记录 ID |
| 购买付款 | 完整成交价 P = D + R | 买家 −R | −D | 订单 ID |
| 成交结算 | 卖家正常入账 S | 卖家 +S | 0 | 订单 ID |
| 押金扣除／违约扣款 | 超时被消耗的押金 D | 买家 0 | −D | 订单 ID |
| 流拍补偿 | 卖家补偿入账 S | 卖家 +S | 0 | 订单 ID |
| 平台收入 | 本单确认的平台收入 F | 不修改用户钱包 | 不修改用户钱包 | 订单 ID |

R 为订单尾款。上述为已确认业务分类，代码枚举命名可在 DDL／接口设计统一。流水表不再强制每条都是两个真实账户之间转账；原 from_account_id／to_account_id 都指向账户行的模型需要调整，最终主体字段及可空约束见 10 的待细化部分。

购买付款记录完整成交价，而非只记尾款。冻结是资产从可用转为占用，不能重复计作消费。平台收入是专门的记账事件，不能假造平台余额变化，也不能计入某个用户的钱包收入。

流水只在对应资金事务成功时留下记录，不另设“处理中／失败”流水状态；任务进度由 Outbox 记录。统计不能把买家支出、卖家入账、平台收入和冻结的正数 amount 简单相加，必须按类型及钱包变化口径解释。

## FUND-05 分账计算与示例

复用纯计算方法：platformFen = totalFen × platformRateBps 整数除以 10,000；sellerFen = totalFen − platformFen。1000 基点为 10%，5000 基点为 50%。平台金额向下取整到分，尾数归卖家；101 分按 50% 分账为平台 50、卖家 51。校验金额范围及乘法溢出。

正常成交用完整成交价作为基数，平台 10%；正尾款超时用本单冻结押金作为基数，平台 50%。订单保存基数、费率、平台收入和卖家入账金额；平台收入流水必须与本单金额一致。

例如用户原有 1000 元，报名冻结 100 元后为可用 900、冻结 100。成交价 230 元，成交事务使买家可用减少 130、冻结减少 100，最终为可用 770、冻结 0；卖家增加 207，平台收入记录 23。购买付款流水金额为 230，可用变化 −130，冻结变化 −100。

未中拍则把冻结 100 转回可用，恢复 1000／0，不产生平台收入。若正尾款超时，消耗冻结 100，卖家入账 50，平台收入 50，买家可用仍为 900；不能写成解冻。

## FUND-06 幂等、锁与事务

充值业务编号唯一；报名 round_id + user_id 唯一；订单 round_id 唯一；每条 flow_id 唯一，流水按 flow_type + biz_id 业务去重。冻结／解冻以报名 ID 关联，购买付款、卖家结算、违约扣款、卖家补偿和平台收入以订单 ID 关联。

正常成交和超时补偿使用同一种平台收入类型及本订单业务键。订单状态竞争保证分支互斥，业务唯一约束避免重复收入。已有流水不能在不核对内容的情况下直接当作本次成功；唯一键冲突不得被吞掉后继续提交余额变化。

任务相关流水编号在创建／持久化任务时建立稳定关联，重投使用原身份。现在一条结算任务会产生多条流水，不能用同一个 flow_id 写三条记录；每种资金效果需要自己的编号。编号集合在 Outbox 载荷中的承载、零尾款兜底与原超时分支的绑定方式仍需详细设计，见 06。

在取得订单／报名记录处理权后，涉及多个用户钱包时，账户 ID 去重并按统一升序加锁，再完成必要的数据库操作。此规则不锁全平台账户，也不进入普通报价 Lua 链路。买卖双方交叉交易仍可能争抢用户账户，不能宣称删除平台账户就绝无死锁；订单、任务等其他行的锁顺序仍需统一。Redis、Kafka、推送等外部操作放在资金事务外。

## FUND-07 资金核对

- 可用余额与冻结金额均不能出现不允许的负数。
- 当前仅有竞拍押金冻结时，单用户 frozen_balance 应等于该用户所有 FROZEN 报名的 deposit_amount 之和；比较须采用一致的已提交视图。
- 正常成交消耗冻结 D 与可用 R，D + R = 成交价 = 卖家入账 + 平台收入。
- 超时补偿消耗冻结 D，D = 卖家补偿 + 平台收入；不再扣尾款，也不返还到可用余额。
- 解冻只恢复对应报名押金，一笔押金只能 RELEASED／APPLIED／FORFEITED 三选一。
- 平台收入流水与订单 platform_amount 一致，逐单去重，冻结中的押金不算营收。
- 在没有提现、外部打款、额外调账且初始余额来源已计入的模拟系统中：累计净充值 = 全部用户可用余额 + 全部用户冻结金额 + 已确认平台收入。冻结不改变等式两边总量。

核对同时检查钱包、报名、订单、流水和任务完成情况，不能只看一个汇总金额相等。
