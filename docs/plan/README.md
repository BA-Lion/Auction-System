# 正式后端模块开发顺序

**2026-11-19 · 已批准。** 下表按开发顺序排列。优先打通竞价和交易，完整大厅最后接入。

| 阶段 | 模块与交付内容 | 前置 | 阶段验收 |
| --- | --- | --- | --- |
| 1 | 账号、会话、钱包开户；接入 MySQL 与 Flyway | 已完成的工程骨架 | 注册同时建立零余额钱包；登录后可查本人身份和余额 |
| 2 | 卖家拍品与场次；保存拍品、立即或预约开场、按 ID 查详情 | 1 的身份能力 | 同一卖家可先保存拍品、之后建场；预约到点开拍，详情可主动刷新 |
| 3 | 钱包充值、余额与流水查询 | 1 的钱包 | 同一充值请求重试只入账一次，余额与流水可核对 |
| 4 | 报名与冻结；场次运行状态、Redis Cluster 与竞价资格衔接 | 2 和 3 | 开拍后仍可报名；卖家报名自己的场被拒；重复报名只冻结一次 |
| 5 | Redis Lua 出价裁决、榜单、尾盘加时、截止同步与报价待发事件 | 4 | 两个实例同时收到同场同价报价时仅一笔通过；详情刷新可取到同版本的价格、榜单和截止 |
| 6 | Kafka 转发、顶层 consumer 落库、个人回执；WebSocket 跨实例推送与重连 | 5 的报价事件和版本化快照 | 同一报价由“已通过”推进到“已记录”；重复投递只落一笔；另一实例上的浏览器可收到变化，漏推后可刷新补齐 |
| 7 | 关场、固定正式结果、交接与订单创建；无人中拍收尾 | 5 的最新截止与关场复核；建单前确认交接方案 | 加时后的旧截止无法提前关场；有赢家时重复交接只生成一单，无有效报价时可流拍 |
| 8 | 订单付款、零尾款结算、未中拍解冻、超时违约及资金 Outbox | 7、钱包和押金记录 | 支付或任务重试后，订单、押金、买卖双方余额和流水一致 |
| 9 | 大厅检索及筛选、PIT 翻页、主动刷新、本人场次历史；整体验收 | 拍品与场次提交事实；报价和关场数据接齐后验完整列表 | 旧游标保持原视图，主动刷新取得新首页；两名用户从大厅进入同场，完成竞价、关场和结算 |

## 已确认的优先级

- 出价功能先服务于竞价中的用户。先让两位竞拍者能轮流出价、看到榜单和截止时间变化，能查询本人报价进度，并在漏推后刷新。随后开发关场与结算。
- 交易流程优先。开发期间通过建场返回的场次 ID 联调。完成关场、付款、解冻和违约处理后，再接入大厅检索、筛选、翻页与刷新。

## 为什么先建场、后充值

注册成功时创建零余额钱包。建场和充值各自只依赖第 1 步。开发时先做拍品与场次，可以尽早拿到真实场次 ID 调试详情。随后接入充值，让竞拍者有足够余额，在第 4 步报名时冻结押金。
